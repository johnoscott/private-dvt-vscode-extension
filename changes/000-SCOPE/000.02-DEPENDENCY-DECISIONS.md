# Dependency Decisions

## External Extension Dependencies

**Target: `extensionDependencies: []`** — Zero hard dependencies on other extensions.

### 1. `samuelcolvin.jinjahtml` → Bundle our own grammar

**Decision:** Remove dependency. Bundle Jinja-SQL TextMate grammar directly.

**Rationale:** The jinjahtml extension provides TextMate grammars for `jinja-sql`, `jinja-yaml`, and `jinja-md`. These are JSON grammar files that can be bundled directly into our extension's `syntaxes/` directory. This is a straightforward extraction — TextMate grammars are declarative JSON and have no runtime code.

**Implementation:**
- Include Jinja-SQL grammar in `syntaxes/jinja-sql.tmLanguage.json`
- Register language contributions in `package.json` under `contributes.grammars`
- Register `jinja-sql` language ID under `contributes.languages`
- Support `.sql` files in dbt project directories as `jinja-sql`

### 2. `ms-python.python` → Optional integration, not required

**Decision:** Remove as hard dependency. Integrate opportunistically when present.

**Rationale:**
- dbt is only one lineage provider — pure SQL users don't need Python at all
- dbt Fusion may not be Python-based
- dbt CLI can be invoked directly via `child_process.spawn` without the Python extension
- Keeping this as a hard dep blocks activation for users who only want SQL lineage or docs

**What the Python extension provides:**
- Python environment / virtualenv discovery
- Interpreter path resolution (finding which `dbt` binary to use)

**Implementation:**
```typescript
// Soft integration — use Python ext when available
const pythonExt = vscode.extensions.getExtension('ms-python.python');
if (pythonExt) {
  const pythonPath = pythonExt.exports.settings.getExecutionDetails().execCommand;
  // Use python path to find dbt in active venv
} else {
  // Fall back: dbt on PATH or user-configured path
  const dbtPath = config.get('dvt.dbtPath') || 'dbt';
}
```

**User experience:**
- dbt users with Python ext installed → automatic venv detection
- dbt users without it → works via `dbt` on PATH or configured path
- Pure SQL users → extension works fully, Python never enters the picture
- dbt Fusion users → works via CLI regardless

### 3. `altimateai.vscode-altimate-mcp-server` → Remove entirely

**Decision:** Remove. No replacement.

**Rationale:** This is a closed-source proprietary extension tied to Altimate AI's SaaS product. DVT is standalone with no proprietary AI features. If MCP server capabilities are needed in the future, they should be implemented directly in the extension.

## Proprietary Package Dependencies

### `@altimateai/dbt-integration` → Replace with own implementation

All dbt project detection, parsing, and command execution will be implemented natively in TypeScript. No dependency on Altimate's npm packages.

### `python-bridge` → Replace with CLI subprocess

Instead of running dbt in-process via a Python bridge, use simple CLI subprocess execution:
- `child_process.spawn('dbt', ['run', '--select', model])`
- Parse JSON output (dbt supports `--log-format json`)
- No Python extension or bridge library needed

### `sqlglot` (vendored Python) → Replace with TypeScript SQL parser

SQL parsing for lineage extraction will be implemented in TypeScript. A purpose-built parser focused on lineage extraction (table refs, column refs, CTEs, joins, subqueries) is significantly simpler than a full SQL transpiler like sqlglot.

For users who have a high-performance CLI available (e.g., a Rust-based parser), the extension will delegate to it via a standard interface.

### `inversify` → Simple module system

The Inversify IoC container adds complexity without proportional benefit for this use case. Use simple TypeScript modules with explicit dependency wiring. If DI is needed, use a lightweight pattern (factory functions or a simple service locator).
